# US-0262 Implementation Plan — Migration 006: Ingest Legacy Top-Level into SQL

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a one-shot JS data migration (`tools/lib/migrations/data_006-ingest-legacy-programme.js`) that ingests the 9 legacy top-level keys of `docs/sdlc-status.json` (`agents`, `metrics`, `stories`, `epics`, `phases`, `cycles`, `currentPhase`, `githubStatus`, `project`) into `sdlc_programme` SQL rows on first `pv:upgrade`, with rollback safety, idempotency, and warning-channel divergence detection — closing the SQL-ingest half of Phase E's hard-gate chain.

**Architecture:** The migration mirrors the Migration 005 precedent (lazy-require Repository, content-addressed `meta_status('migration_006_hash')` idempotency, raw SQL writes through `repo.index`) but with three substantive differences: (a) writes happen inside a single explicit `BEGIN/COMMIT` SQL transaction with `ROLLBACK` on any error — partial-failure safety per spec §4.2 risk R4; (b) `SdlcProgrammeRepo.set()` is bypassed in favor of raw `INSERT...ON CONFLICT` SQL so the mirror is rendered exactly **once** after commit instead of 9 times during the loop; (c) state-C divergence (json[K] ≠ programme[K]) logs `migration_006_conflict_{K}` via `repo.warningsChannel.append()` rather than overwriting SQL. The migration does NOT strip top-level legacy keys — that happens organically when US-0261 deletes the `sdlc-mirror.js` preservation block. The per-migration snapshot (`docs/.pv-backup/pre-data_006-ingest-legacy-programme/`) is captured automatically by the runner because the migration declares `touches = ['docs/sdlc-status.json']`. The broader `pv:upgrade` snapshot (`pre-upgrade-<ts>/`) already captures the JSON mirror, so the rollback roundtrip works without further `pv:upgrade` changes.

**Tech Stack:** Node ≥20, Jest, `better-sqlite3` via `tools/lib/repository`, `tools/lib/migrations/index.js` (runner), `tools/lib/migrations/backup.js` (per-migration snapshot helper), `tools/lib/repository/warnings-channel.js`.

```js
'use strict';

/**
 * Migration 006 — ingest legacy top-level docs/sdlc-status.json keys into
 * sdlc_programme SQL rows.
 *
 * Phase E (EPIC-0045) story US-0262 / AC-1019. Companion spec §4.2.
 *
 * The 9 legacy top-level keys (agents, metrics, stories, epics, phases,
 * cycles, currentPhase, githubStatus, project) move under programme.{key}.
 * Migration 006 ingests them on first `pv:upgrade`:
 *
 *   - State A (canonical-only, no legacy top-level): no-op, hash persisted.
 *   - State B → C (legacy-only, empty programme): each key INSERT'd into
 *     sdlc_programme inside one BEGIN/COMMIT transaction; one mirror
 *     re-render after commit.
 *   - State C (preservation-doubled, populated programme): divergence
 *     between json[K] and programme[K] logged via warningsChannel as
 *     `migration_006_conflict_{K}`; SQL value unchanged.
 *
 * Migration 006 does NOT strip the legacy top-level keys. The strip
 * happens organically when US-0261 removes the sdlc-mirror.js
 * preservation block — the next mirror write naturally produces canonical
 * shape because the preservation no longer copies legacy keys forward.
 *
 * Why bypass SdlcProgrammeRepo.set(): the convenience helper does
 * INSERT...ON CONFLICT followed by `await this.mirror.write()` per call.
 * Calling it 9 times inside a transaction would (a) trigger 9 mirror
 * writes that read uncommitted SQL state, (b) break transactional
 * rollback (the first 8 mirror writes already touched disk before the
 * 9th failed), and (c) acquire the mirror file lock 9 times. Raw SQL
 * inside the txn + one mirror write after commit is the only correct
 * shape.
 */

const fs = require('fs');
const path = require('path');
const crypto = require('crypto');

const HASH_KEY = 'migration_006_hash';
const touches = ['docs/sdlc-status.json'];

// The 9 legacy top-level keys, in stable iteration order. Stable order
// matters for log output and for the SQL transaction's per-key INSERT
// sequence (which is observable in a divergence-warning trace).
const LEGACY_KEYS = [
  'agents',
  'metrics',
  'stories',
  'epics',
  'phases',
  'cycles',
  'currentPhase',
  'githubStatus',
  'project',
];

async function up({ root }) {
  const file = path.join(root, 'docs', 'sdlc-status.json');
  if (!fs.existsSync(file)) return { skipped: 'no-file' };

  const { Repository } = require('../repository');
  Repository._reset();
  const repo = Repository.getInstance({ root });

  try {
    // Hash-based idempotency — same pattern as Migration 005. The hash is
    // computed over the post-mirror canonical bytes so subsequent runs
    // recognise a previously-ingested state even after the mirror has
    // re-rendered.
    const buf = fs.readFileSync(file);
    const currentHash = crypto.createHash('sha256').update(buf).digest('hex');
    const existing = repo.index.prepare('SELECT value FROM meta_status WHERE key=?').get(HASH_KEY);
    if (existing && existing.value === currentHash) {
      return { skipped: 'idempotent' };
    }

    // Skeleton — state-B/C ingest + divergence detection land in Tasks 2-4.
    // For now: read the current programme-row state and the on-disk JSON
    // so the hash + counts can be persisted truthfully.
    const programmeFromSql = repo.sdlcProgramme.all();
    let data;
    try {
      data = JSON.parse(buf.toString('utf8'));
    } catch (e) {
      throw new Error(`Migration 006: could not parse ${file}: ${e.message}`, { cause: e });
    }

    let ingested = 0;
    // Tasks 2-4 fill in the per-key INSERT loop here.
    // No-op for now means: state-A repos pass straight through, state-B/C
    // pass through too but without ingesting (the next task adds writes).

    // After (eventual) commit, re-render the mirror exactly once. Because
    // Task 1 doesn't write anything, the mirror re-render is unnecessary
    // until Task 2 — but persisting the hash now is required so the
    // idempotency check on a second run recognises the state.

    const mirrorBuf = fs.readFileSync(file);
    const mirrorHash = crypto.createHash('sha256').update(mirrorBuf).digest('hex');
    repo.index
      .prepare(
        `INSERT INTO meta_status(key,value) VALUES(?,?)
         ON CONFLICT(key) DO UPDATE SET value=excluded.value`,
      )
      .run(HASH_KEY, mirrorHash);

    // Suppress unused-var lint: programmeFromSql + data + LEGACY_KEYS will
    // be consumed in Tasks 2-4. Reference them once each so the linter
    // does not flag dead code.
    void programmeFromSql;
    void data;
    void LEGACY_KEYS;

    return { ingested };
  } finally {
    Repository._reset();
  }
}

module.exports = { up, touches, HASH_KEY };
```

    }
    // State A (!inJson, *) and state-C-synced/divergent paths handled

} catch (e) {

  throw e;

// reflects the new programme rows. Per-key mirror writes during the
// loop would (a) read uncommitted SQL inside the txn, (b) acquire
// the file lock 9 times, (c) break rollback semantics. One write here
// is the only correct shape.
